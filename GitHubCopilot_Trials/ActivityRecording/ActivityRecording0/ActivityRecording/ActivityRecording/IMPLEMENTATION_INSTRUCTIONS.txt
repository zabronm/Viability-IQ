ACTIVITY RECORDING SERVICE - IMPLEMENTATION GUIDE
================================================

PURPOSE
-------

This package introduces a centralized activity writer and connects it to:

- successful form login;
- successful logout;
- successful registration;
- real password changes;
- generic repository create/update/delete operations;
- Bank and LoanType writes in MasterDataService.

No password, password confirmation, reset token or credential payload is
written to the activity table.

LOGIN.RAZOR.CS
--------------

Login.razor.cs is intentionally not replaced. Read LOGIN_COMPONENT_NOTE.txt.

The browser posts Login.razor directly to /api/auth/signin-form. Only
AuthController knows whether authentication succeeded, so logging in the
component would create false events.


GENERIC REPOSITORY TRANSACTION BEHAVIOUR
----------------------------------------

The replacement GenericDataRepository performs each create/update/delete and
its activity INSERT using the same connection and SQL transaction.

If activity recording fails:

- the business write is rolled back;
- the exception is propagated;
- the UI must display its normal failure notification.

This is appropriate for business data where an audit trail is mandatory.

The repository explicitly excludes ActivityLog itself from automatic recording,
preventing recursive activity rows.

Only write operations are automatic. Generic read operations are not logged
because internal data loading would otherwise generate excessive and misleading
"View" entries. Record meaningful views explicitly after authorization and
successful page/entity loading; see EXPLICIT_ACTIVITY_EXAMPLES.txt.


IDENTITY OPERATION BEHAVIOUR
----------------------------

ASP.NET Identity operations and tblActivityLog do not currently share a single
database transaction. Therefore:

- login/registration/password/logout completes first;
- activity recording is attempted afterward;
- an audit failure is written as a server error;
- the already-successful identity action is not reported to the user as failed.

For strict atomic identity auditing, introduce an outbox table written in the
same IdentityDbContext transaction and process it with retries. Do not attempt
to reverse a completed password change or login when an audit INSERT fails.


CHANGE PASSWORD
---------------

The supplied ChangePassword component previously simulated success with:

    await Task.Delay(800);

The replacement resolves the authenticated user and calls:

    IPasswordService.ChangePasswordAsync(...)

An activity is recorded only when PasswordChangeResult.Success is true.


REGISTER / EDIT PROFILE
-----------------------

Registration is logged after AuthService.RegisterAsync succeeds.

The supplied edit-profile branch also simulated success using Task.Delay.
The replacement does not create a false Update event. It displays:

    Profile editing has not yet been connected to a persistence service.

Connect that branch to a real user-profile update service before recording an
ActivityAction.Update event.

The Province and Branch lists are still hard-coded in the supplied component.
Replacing those lookups is separate from activity recording and remains a
required production task.


LOGOUT
------

Logout must mutate the authentication cookie in a real HTTP request, not inside
an interactive Blazor circuit. The replacement Logout.razor presents a compact
confirmation form that posts with an antiforgery token to:

    /api/auth/signout-form

AuthController captures the authenticated ApplicationUser before sign-out,
persists the mandatory Logout activity with the captured user ID and actor
name, then completes sign-out and redirects to /login.

The order is intentional:

1. Resolve the authenticated user.
2. Write the Logout activity.
3. Clear the authentication cookie.

If the activity INSERT fails, sign-out is stopped and the user remains
authenticated. The Logout page displays an operational error and permits a
retry. This enforces the invariant that no completed logout is missing its
activity row.

The activity description says "initiated secure sign out" because cookie
sign-out occurs immediately after the database write. For absolute atomicity
between the database and HTTP cookie, use a durable outbox; SQL transactions
cannot include browser-cookie mutation.

Do not move SignInManager.SignOutAsync back into Logout.razor. Interactive
server components cannot reliably modify response cookies after the original
HTTP response has completed.


MASTER DATA SERVICE - MANUAL INTERVENTION REQUIRED
--------------------------------------------------

Do not overwrite the full 550-line MasterDataService from a text handoff.
Apply the focused replacements in:

    MASTER_DATA_SERVICE_CHANGES.txt

That guide changes:

- constructor injection;
- SaveBankAsync;
- DeleteBankAsync;
- SaveLoanTypeAsync;
- DeleteLoanTypeAsync.

Each replacement uses one transaction for the master-data write and activity
write.

Do not auto-log raw ExecuteAsync, ExecuteCommandAsync or UpdateFieldAsync calls.
Those methods lack reliable entity and action semantics. Migrate important
writes to typed methods or add purpose-specific transactional methods.


ACTIVITY ENTITY TYPES
---------------------

The writer accepts EntityType as a string because GenericDataRepository<T>
supports more domain types than the original enum. The expanded enum is included
so the Activity Log page filter exposes common master-data types such as Bank,
LoanType, Province and ProductCategory.

When adding a new important domain entity:

1. add it to ActivityEntityType for filtering;
2. generic recording will still function before that enum update;
3. use nameof(ActivityEntityType.X) in explicit calls.


CONTEXT CAPTURE
---------------

ActivityLogWriter captures:

- explicit user/actor values when supplied;
- otherwise authenticated claims or ISessionService context;
- assessment context from the request or current session;
- request path;
- IP address;
- user agent;
- trace/correlation identifier;
- UTC timestamps.

HttpContext may not be available during every Blazor circuit operation. In that
case IP/user-agent/request context can be null, while session and explicit
business context are still recorded.


METADATA SAFETY
---------------

Never pass complete entities, form models or requests as Metadata.

Allowed examples:

- report output format;
- changed field names;
- import row counts;
- workflow stage.

Never record:

- passwords or confirmation passwords;
- reset or authentication tokens;
- cookies;
- complete financial payloads;
- identity documents;
- connection strings.


ACTIVITY FAILURE MONITORING
---------------------------

ActivityLogWriter logs and rethrows every database failure. Configure production
logging alerts for:

    "Failed to record"
    "activity recording failed"
    "was not written to the activity log"

For mission-critical audit completeness, add monitoring that compares expected
business actions with activity volume and alerts on gaps.


VALIDATION
----------

After copying files and applying MasterDataService changes:

1. Run:

       dotnet build .\ViabilityIQ.Web\ViabilityIQ.Web.csproj

2. Register a test user and confirm one Create/User activity.
3. Sign in and confirm one Login/User activity.
4. Change the password and confirm one Update/User activity.
5. Sign out and confirm one Logout/User activity.
6. Create, update and delete one typed generic entity.
7. Confirm each operation produces exactly one activity.
8. Force an activity INSERT failure in a non-production database and confirm a
   generic business write rolls back.
9. Save and delete a Bank and LoanType after applying the focused changes.
10. Confirm no ActivityLog write recursively creates another ActivityLog row.

Also verify:

11. An inactive user receives the same generic invalid-credentials response.
12. Invalid login redirects to /login?error=InvalidCredentials.
13. Logout displays confirmation, POSTs successfully and clears the cookie.
14. Temporarily make tblActivityLog unavailable and confirm logout is stopped,
    the user remains authenticated, and the Logout page displays AuditFailure.
